# 003 Struct Tags And Generation

## Contract

Struct tags are a validation language. A tag should mean one thing before it
reaches runtime reflection or code generation.

`pkg/tagparser` owns tag syntax and semantic compilation. Runtime reflection and
`cmd/gozodgen` may render different backends, but neither should independently
decide what a tag means.

## Field Plans

`tagparser.CompileFieldPlan` is the semantic boundary for a struct field. A
field plan owns:

- ordered validation operations
- default and prefault operations
- pointer optionality
- generated optional placement
- runtime optional placement
- enum, regex, literal, and string-format rule meaning

Generated code may still render typed values, imports, and Go syntax, but it
must consume the compiled plan instead of reinterpreting raw tags.

Optional placement is semantic. A pointer field with a default or prefault must
preserve whether `.Optional()` belongs before or after the default/prefault
operation so generated schemas and reflection schemas parse nil and missing
inputs the same way.

## Runtime And Generated Parity

Behavior tests should cover both reflection and generated schemas for:

- required and optional fields
- pointer optionality
- defaults and prefaults
- enum and regex rules
- string format rules
- numeric and length checks
- error paths for malformed tags

Source-shape tests may protect generated code only where shape is part of the
contract, such as optional/default ordering or required imports.

## Generated Artifacts

Generated code should change only when inputs or generator logic change.

The generated file header is stable:

```go
// Code generated by gozodgen. DO NOT EDIT.
```

Generation timestamps do not belong in generated files. Golden tests compare the
real generated output and should not normalize away unstable timestamp lines.
